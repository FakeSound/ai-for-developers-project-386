# Пользовательские сценарии

Список того, что должно работать в приложении целиком — от клика в браузере
до записи в хранилище бэкенда. Это же список проверяется автоматически:
идентификатор сценария стоит в заголовке соответствующего теста, так что
связь документа и кода ищется грепом.

```bash
npm run e2e                       # весь список
npx playwright test -g "Г-3"      # один сценарий
```

Роли — те же, что в контракте: **гость** (анонимный посетитель, префикс `Г`)
и **владелец календаря** (заранее заданный профиль, префикс `В`).
Авторизации нет, админская часть отличается только маршрутом.

Общие предусловия для всех сценариев:

- бэкенд поднят и засеян демо-данными (`backend/app/seed.py`): владелец
  «Анна Смирнова», типы событий `znakomstvo`, `konsultaciya`, `bystryj-zvonok`
  и несколько броней;
- время показывается в поясе владельца `Europe/Moscow`;
- окно записи — 14 дней от текущей даты, рабочие часы 10:00–18:00 по будням.

## Сценарии гостя

### Г-1. Гость видит виды встреч с длительностью

`e2e/tests/guest-booking.spec.ts`

1. Открыть `/`.
2. **Ожидаемо:** заголовок «Записаться на встречу», имя владельца в шапке,
   карточки «Знакомство» (30 минут), «Консультация» (1 час) и «Быстрый звонок»
   (15 минут) с названием, описанием и длительностью.

### Г-2. Страница вида встречи открывается на ближайшем свободном дне

`e2e/tests/guest-booking.spec.ts`

1. Открыть `/`, перейти по карточке «Знакомство».
2. **Ожидаемо:** заголовок вида встречи, бейджи длительности и
   `Europe/Moscow · GMT+3`; в календаре выбран первый день окна, где есть
   свободное время; список времени открыт на нём, первым идёт самое раннее
   время дня; рядом счётчик свободных слотов.

### Г-3. Гость бронирует слот и получает подтверждение

`e2e/tests/guest-booking.spec.ts`

1. Открыть страницу «Знакомство», нажать на первое свободное время.
2. В диалоге «Подтвердите запись» заполнить имя, почту и комментарий.
3. Нажать «Записаться».
4. **Ожидаемо:** диалог переключается на «Встреча забронирована» и показывает
   почту, имя, комментарий, диапазон времени и номер брони из ответа сервера.

### Г-4. Забронированное время исчезает из календаря

`e2e/tests/guest-booking.spec.ts` · продолжение Г-3

1. Закрыть подтверждение, вернуться к тому же виду встречи.
2. Выбрать день, на который была запись.
3. Перезагрузить страницу и выбрать день снова.
4. **Ожидаемо:** кнопки этого времени в сетке нет — ни в обновлённом кэше
   клиента, ни в свежем ответе сервера.

### Г-5. Бронь гостя видна владельцу в списке встреч

`e2e/tests/guest-booking.spec.ts` · продолжение Г-3

1. Открыть `/admin`.
2. **Ожидаемо:** в списке предстоящих встреч есть строка с именем гостя,
   его почтой, комментарием, типом события и временем брони.

### Г-6. Слот, занятый во время заполнения формы, отдаёт конфликт

`e2e/tests/guest-booking.spec.ts`

1. Открыть страницу «Быстрый звонок», нажать на свободное время — диалог открыт.
2. Пока форма заполняется, это же время занимает другая запись (тест создаёт
   её через API — конфликт настоящий, ответ не подменяется).
3. Заполнить форму и нажать «Записаться».
4. **Ожидаемо:** появляется сообщение «Это время уже заняли», диалог
   закрывается, календарь перезапрошен и занятого времени в сетке больше нет.

Проверяет правило глобальной занятости: время заняли под **другим** типом
события, но слот исчез и здесь.

### Г-7. Форма брони не пропускает пустое имя и неверную почту

`e2e/tests/guest-errors.spec.ts`

1. Открыть страницу «Консультация», выбрать время, нажать «Записаться»
   с пустой формой.
2. **Ожидаемо:** «Укажите, как к вам обращаться» и «Похоже на опечатку
   в адресе почты».
3. Заполнить имя, ввести почту `не-почта`, отправить снова.
4. **Ожидаемо:** ошибка имени ушла, ошибка почты осталась, диалог остался
   на шаге формы, бронь не создана.

### Г-8. Несуществующий вид встречи показывает понятную ошибку

`e2e/tests/guest-errors.spec.ts`

1. Открыть `/event-types/net-takogo-vida`.
2. **Ожидаемо:** «Такого вида встреч нет», ссылка «К видам встреч» возвращает
   на список.

### Г-9. Неизвестный адрес возвращает на список видов встреч

`e2e/tests/guest-errors.spec.ts`

1. Открыть `/takoy-stranicy-net`.
2. **Ожидаемо:** «Страница не найдена» и рабочая кнопка возврата.

## Сценарии владельца календаря

### В-1. Созданный тип события сразу доступен гостю

`e2e/tests/owner-event-types.spec.ts`

1. Открыть `/admin/event-types`, заполнить идентификатор, название, описание
   и длительность, нажать «Создать».
2. **Ожидаемо:** сообщение «Тип события создан», карточка появилась в списке
   с идентификатором и длительностью, форма очистилась.
3. Открыть `/`, перейти по новому виду встречи.
4. **Ожидаемо:** страница открывается, по новому типу считаются свободные слоты.

### В-2. Идентификатор проверяется по правилам контракта

`e2e/tests/owner-event-types.spec.ts`

1. Ввести идентификатор `Bad Id!` и создать.
2. **Ожидаемо:** «Только строчные латинские буквы, цифры и дефис между ними».
3. Ввести уже занятый `znakomstvo` и создать.
4. **Ожидаемо:** «Такой идентификатор уже занят — выберите другой» —
   ошибка `409` от бэкенда показана прямо на поле.

### В-3. Встречи сгруппированы по дням и показывают гостя

`e2e/tests/owner-bookings.spec.ts`

1. Создать бронь, открыть `/admin`.
2. **Ожидаемо:** заголовок «Предстоящие встречи» со счётчиком; строка брони
   с временем начала и конца, именем гостя, типом события, длительностью
   и комментарием; строка находится в секции своего календарного дня.

### В-4. Навигация ведёт по разделам приложения

`e2e/tests/owner-bookings.spec.ts`

1. Пройти по пунктам «Встречи», «Типы событий», «Запись».
2. **Ожидаемо:** каждый ведёт на свой экран.

## Что осознанно не покрыто

- **Мок Prism (`npm run dev:mock`)** и селектор сценариев ответа — вспомогательный
  режим разработки, из продакшен-сборки он вырезан.
- **Ошибки загрузки и состояния «данных нет»** — требуют подмены ответов сервера
  и проверяют отрисовку, а не сквозной путь. Бизнес-правила за ними
  (границы окна записи, попадание в сетку, параллельные брони) закрыты тестами
  бэкенда в `backend/tests/`.
- **Тёмная тема и адаптив** — визуальные, дешевле проверять глазами.

## Как это устроено технически

- Прогон строго последовательный (`workers: 1`). Бэкенд хранит данные в памяти
  одного процесса, а занятость календаря глобальная: параллельные воркеры
  дрались бы за одни и те же слоты.
- Состояние между тестами не откатывается, поэтому сценарии никогда не проверяют
  точные количества и создают свои данные с уникальными идентификаторами.
- Сид-брони как якорь не используются: `backend/app/seed.py` пропускает те,
  чьё время уже прошло, — на вечернем прогоне их бы не было.
- Предусловия, которые через интерфейс не собрать (например, занять слот
  в момент заполнения формы), тесты готовят через API — тот же адрес,
  что и у приложения, типы берутся из контракта.
