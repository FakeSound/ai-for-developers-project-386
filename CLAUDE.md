# AICalls — инструкции для агента

Сервис бронирования встреч. Контракт на TypeSpec — единственный источник правды,
под него написаны бэкенд на FastAPI и фронтенд на React.

## Коммиты — обязательно

Формат сообщений — **Conventional Commits**, соглашение целиком в
[CONTRIBUTING.md](CONTRIBUTING.md). Коротко:

- `<тип>(<скоуп>): <заголовок>`; типы — `feat`, `fix`, `docs`, `style`,
  `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`;
- скоупы — `contract`, `backend`, `frontend`, `e2e`, `ci`, `docs`, `deps`
  (скоуп необязателен, но чужих не выдумывать);
- заголовок на русском, в повелительном наклонении, со строчной буквы,
  без точки, до 100 символов;
- ломающее изменение — `!` и футер `BREAKING CHANGE:`;
- в футер каждого своего коммита добавлять:

  ```
  Co-Authored-By: Claude <noreply@anthropic.com>
  ```

Сообщение проверяет хук `.husky/commit-msg`; `--no-verify` не использовать —
в CI те же правила, и PR всё равно не пройдёт.

**Коммитить только по явной просьбе.** Не коммитить и не пушить «за компанию»
с правкой. Один коммит — одно осмысленное изменение.

Заголовок PR тоже по Conventional Commits: в `main` мёрджим squash-мёрджем,
и именно заголовок PR читает release-please.

## Версии и changelog

`CHANGELOG.md`, `.release-please-manifest.json` и поля `version` ведёт
release-please. Руками их не править — версия поднимется сама из типов коммитов.

## Устройство проекта

```
main.tsp                 контракт — единственный источник правды
openapi/openapi.yaml     сгенерированный OpenAPI (в git, правится только через main.tsp)
backend/                 FastAPI, хранилище в памяти процесса
frontend/                Vite + React + shadcn/ui
frontend/src/api/schema.d.ts   типы, сгенерированные из контракта, вручную не править
e2e/                     сквозные сценарии на Playwright
docs/scenarios.md        описание пользовательских сценариев
```

После правки `main.tsp` обязательно `npm run gen:api` — иначе клиент разойдётся
с контрактом, и сборка упадёт.

## Команды

```bash
npm run dev        # бэкенд :3000 + фронтенд :5173
npm run api:test   # тесты бэкенда (pytest)
npm run e2e        # сквозные сценарии (сам поднимает бэкенд и собранный фронтенд)
npm run e2e:ui     # тот же прогон в интерактивном режиме
npm run gen:api    # main.tsp -> openapi.yaml -> schema.d.ts
```

## Что учитывать при правках

- **Бизнес-правила живут на сервере.** Сетка слотов, окно записи и проверка
  занятости — в `backend/app/scheduling.py`; фронтенд только показывает то,
  что вернул сервер, и ничего не пересчитывает сам.
- **Занятость календаря глобальная**: время, занятое бронью любого типа события,
  недоступно для всех остальных.
- **Данные бэкенда живут в памяти процесса** и сбрасываются при перезапуске.
  Поэтому e2e гоняются в один воркер и не рассчитывают на чистое состояние:
  свои данные создают с уникальными идентификаторами и не проверяют
  точные количества.
- **Время показывается в поясе владельца** (`Europe/Moscow`), а не браузера;
  пояс всегда передаётся в функции форматирования явно.
- **Тексты интерфейса на русском.** Селекторы e2e построены на ролях и видимом
  тексте — меняя формулировку на экране, поправить и сценарий.
- `.github/workflows/hexlet-check.yml` не трогать.

## Правки в e2e

Новый сценарий сначала описывается в [docs/scenarios.md](docs/scenarios.md)
с идентификатором (`Г-N` для гостя, `В-N` для владельца), затем этот же
идентификатор ставится в заголовок теста. `data-testid` в приложение
не добавлять: форм и кнопок хватает через роли, подписи и `label`.
