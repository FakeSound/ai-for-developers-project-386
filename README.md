# AICalls

**Приложение развёрнуто: <https://aicalls.onrender.com>**

Сервис бронирования встреч. Контракт описан в [`main.tsp`](main.tsp) на TypeSpec,
под него собраны бэкенд на Python и фронтенд на React.

Две роли, без регистрации и авторизации:

- **Владелец календаря** — один заранее заданный профиль. Создаёт типы событий
  и смотрит список предстоящих встреч.
- **Гость** — анонимный посетитель. Выбирает вид встречи, свободный слот
  в ближайшие 14 дней и оставляет имя с почтой.

Занятость календаря глобальная: на одно и то же время нельзя создать две записи,
даже если это разные типы событий.

## Запуск

Нужны Node.js и Python 3.11+ (`python3.11` в PATH).

```bash
npm run install:all   # зависимости в корне, во frontend/ и venv бэкенда
npm run dev           # бэкенд на :3000 и фронтенд на :5173
```

Открыть <http://localhost:5173>.

Отдельно:

```bash
npm run spec                    # main.tsp -> openapi/openapi.yaml
npm run gen:api                 # openapi.yaml -> frontend/src/api/schema.d.ts
npm run api                     # только бэкенд на :3000 (с автоперезагрузкой)
npm run api:test                # тесты бэкенда
npm run e2e                     # сквозные сценарии в браузере
npm --prefix frontend run dev   # только фронтенд
npm run build                   # спека + продакшен-сборка фронтенда
npm run dev:mock                # старый режим: мок Prism вместо бэкенда
```

## Запуск в Docker

Нужен только Docker — ни Node, ни Python на машине не требуется.

```bash
docker build -t aicalls .
docker run --rm -e PORT=8080 -p 8080:8080 aicalls
```

Открыть <http://localhost:8080>. То же самое через compose:

```bash
docker compose up -d --build    # http://localhost:8080
docker compose logs -f          # логи
docker compose down             # остановить и удалить контейнер
```

Приложение целиком в одном образе и в одном процессе: `uvicorn` отвечает по
адресам контракта и он же отдаёт собранный фронтенд. Браузер ходит на один
origin, поэтому CORS не задействован, а `baseUrl` клиента остаётся тем же
относительным путём, что и в разработке.

Порт берётся из переменной окружения `PORT` (без неё — 3000): так запускает
и хостинг, и автоматическая проверка проекта.

Раздачей статики занимается `backend/app/web.py`:

```
/api/v1/...      маршруты контракта
/assets/...      файлы сборки, кэш навсегда — имена хэширует Vite
/favicon.svg     остальные файлы из frontend/public
всё прочее       index.html: маршруты вроде /admin знает только react-router
```

Неизвестный адрес под `/api/v1` остаётся ошибкой контракта в JSON — оболочка
приложения отдаётся только там, где её ждёт браузер.

Данные, как и при локальном запуске, живут в памяти процесса: перезапуск
контейнера возвращает хранилище к демо-данным.

Образ собирается из готовых артефактов репозитория — `openapi/openapi.yaml`
и `frontend/src/api/schema.d.ts` лежат в git, поэтому компиляция TypeSpec
в сборку не входит. После правки `main.tsp` нужно выполнить `npm run gen:api`
и пересобрать образ.

Сквозные сценарии умеют гоняться по запущенному контейнеру:

```bash
E2E_BASE_URL=http://localhost:8080 npx playwright test
```

## Деплой

Приложение опубликовано на Render: <https://aicalls.onrender.com>

Render собирает тот же корневой `Dockerfile` и передаёт контейнеру `PORT` —
никакой отдельной конфигурации сборки нет. Настройки сервиса описаны
в [`render.yaml`](render.yaml), так что его можно пересоздать из репозитория
(Dashboard -> New -> Blueprint). Каждый пуш в отслеживаемую ветку запускает
новый деплой.

Что стоит знать про этот стенд:

- план free — сервис засыпает без трафика, первый запрос после простоя
  занимает 30–60 секунд;
- данные живут в памяти процесса, поэтому засыпание или новый деплой
  возвращают календарь к демо-данным;
- сквозные сценарии можно прогнать прямо по нему:
  `E2E_BASE_URL=https://aicalls.onrender.com npx playwright test`.

## Структура

```
main.tsp                 контракт — единственный источник правды
tspconfig.yaml           настройка эмиттера @typespec/openapi3
openapi/openapi.yaml     сгенерированный OpenAPI 3.0
backend/                 бэкенд на FastAPI: реализация контракта
mock/dataset.mjs         мок-данные: владелец, типы событий, брони, сетка слотов
mock/build-mock.mjs      добавляет примеры в OpenAPI -> mock/openapi.mock.yaml
frontend/                приложение на Vite + React + shadcn/ui
e2e/                     сквозные сценарии на Playwright
docs/scenarios.md        пользовательские сценарии, которые проверяет e2e
Dockerfile               образ приложения: сборка фронтенда -> uvicorn c ней внутри
docker-compose.yml       локальный запуск того же образа с PORT=8080
render.yaml              blueprint деплоя: сервис на Render по этому Dockerfile
```

Типы фронтенда генерируются из `openapi/openapi.yaml` в
`frontend/src/api/schema.d.ts` и вручную не правятся. После изменения `main.tsp`
нужно выполнить `npm run gen:api` — сборка упадёт, если клиент разошёлся
с контрактом.

## Бэкенд

FastAPI, один процесс на порту 3000 (в контейнере — на `PORT`), все маршруты
под префиксом `/api/v1` — ровно те адреса, что объявлены в контракте.
Авторизации нет: владелец — заранее заданный профиль в `backend/app/config.py`,
гость анонимен, админская часть отличается только маршрутом.

```
backend/app/models.py       схемы контракта на pydantic (snake_case -> camelCase)
backend/app/scheduling.py   сетка слотов, окно записи, проверки времени
backend/app/store.py        хранилище в памяти
backend/app/seed.py         демо-данные, перенос mock/dataset.mjs
backend/app/routers/        по одному модулю на группу операций контракта
backend/app/web.py          раздача сборки фронтенда: только в Docker-образе
backend/tests/              pytest поверх TestClient
```

Бизнес-правила целиком на сервере:

- слоты не хранятся, а вычисляются из расписания владельца (будни 10:00–18:00
  `Europe/Moscow`, шаг 30 минут), длительности типа события и уже созданных броней;
- занятость календаря глобальная — пересечение с бронью **любого** типа события
  убирает слот из выдачи и даёт `409 slot_taken` при попытке записи;
- окно записи — 14 дней от текущей даты; вне его `409 slot_out_of_window`,
  мимо сетки — `409 slot_not_in_grid`;
- проверка занятости и вставка брони выполняются под одним локом, поэтому
  два одновременных запроса на один слот не создадут две встречи.

**Данные живут в памяти процесса и сбрасываются при перезапуске** — отдельная
база на этом шаге не нужна. При старте хранилище засевается теми же типами
событий и бронями, что были в моке, поэтому окно записи всегда начинается
с сегодняшнего дня.

Документация запущенного бэкенда: <http://localhost:3000/docs>.
Тесты (`npm run api:test`) проверяют бизнес-правила и сверяют набор операций
с `openapi/openapi.yaml`.

## Сквозные тесты

Пользовательские сценарии описаны в [`docs/scenarios.md`](docs/scenarios.md)
и проверяются автоматически: идентификатор сценария (`Г-3`, `В-1`, …) стоит
в заголовке теста, так что документ и код не разъезжаются.

```bash
npm run e2e                     # весь набор
npm run e2e:ui                  # интерактивный режим
npm run e2e:report              # отчёт последнего прогона
npx playwright test -g "Г-3"    # один сценарий
```

Тесты на TypeScript, типы для запросов к API берутся из того же
`schema.d.ts`, что и в приложении, — расхождение с контрактом не пройдёт молча.

Приложение поднимает сам Playwright: uvicorn на 3000 и `vite preview` на 4173
с прокси на бэкенд. Браузер, как и в проде за nginx, ходит на один origin.
Отдельно ничего запускать не нужно, сборка фронтенда входит в прогон.
Готовое окружение подставляется переменной `E2E_BASE_URL`.

Прогон строго последовательный: бэкенд хранит данные в памяти одного процесса,
а занятость календаря глобальная — параллельные воркеры дрались бы за слоты.

## Коммиты и релизы

Формат коммитов — [Conventional Commits](CONTRIBUTING.md), проверяется локальным
хуком, джобой `commitlint` по коммитам PR и отдельной проверкой заголовка PR.
Правила общие для людей и для агента, для агента они продублированы
в [`CLAUDE.md`](CLAUDE.md).

Версию и `CHANGELOG.md` ведёт release-please: после мёрджа в `main` он создаёт
или обновляет PR `chore(main): release X.Y.Z`, а мёрдж этого PR ставит тег
и публикует релиз. Версия одна на весь репозиторий; руками её не правят.

```
.github/workflows/e2e.yml              сквозные сценарии на каждый PR и push в main
.github/workflows/commits.yml          Conventional Commits: коммиты ветки и заголовок PR
.github/workflows/release-please.yml   release-PR с changelog и версией
```

Чтобы release-please мог создавать PR, в настройках репозитория должно быть
включено Settings → Actions → General → Workflow permissions →
«Allow GitHub Actions to create and approve pull requests».

## Мок Prism

Мок остался как запасной режим и больше не нужен для работы приложения:
`npm run dev:mock` поднимает Prism вместо бэкенда и включает `VITE_MOCK=true`
из `frontend/.env.mock`.

### Как устроен мок

`npm run mock` компилирует контракт, собирает мок-спеку и поднимает Prism.
Мок-данные пересчитываются от текущей даты при каждом запуске, поэтому окно
записи всегда начинается с сегодняшнего дня.

Владелец в моке принимает встречи по будням с 10:00 до 18:00 (`Europe/Moscow`)
с шагом 30 минут; в календаре засеяно несколько броней, и пересекающиеся с ними
слоты из выдачи исключены — по ним видно правило глобальной занятости.

Prism монтирует роуты в корень и игнорирует путь из `servers`, поэтому базовый
путь `/api/v1` переносится в ключи `paths` при сборке мок-спеки. Мок отвечает
ровно по адресам из контракта, а Vite проксирует на него `/api/v1`.

### Выбор ответа заголовком `Prefer`

Prism не хранит состояние и без подсказки отдаёт первый пример из спеки.
Нужный выбирается его штатным заголовком `Prefer`:

```bash
curl -s localhost:3000/api/v1/owner
curl -s -H 'Prefer: example=konsultaciya' \
  localhost:3000/api/v1/event-types/konsultaciya/slots
curl -s -X POST localhost:3000/api/v1/bookings \
  -H 'content-type: application/json' \
  -H 'Prefer: code=409, example=slot_taken' \
  -d '{"eventTypeId":"znakomstvo","startsAt":"2026-08-17T07:00:00Z",
       "guest":{"name":"Иван","email":"ivan@example.com"}}'
```

Фронтенд делает то же самое: в мок-режиме (`VITE_MOCK=true` в
`frontend/.env.mock`) он подставляет `Prefer: example=<id>`, чтобы карточка
и слоты соответствовали выбранному типу события. С бэкендом флаг равен `false`,
заголовок не отправляется, и остальной код не меняется.

Валидацию запросов Prism выполняет сам: на некорректное тело он отвечает
контрактным `400 validation_failed`.

### Ограничения мока

Prism отдаёт заготовленные примеры и не хранит состояние, поэтому:

- созданная бронь не исчезает из сетки слотов и не появляется в списке
  предстоящих встреч;
- в подтверждении показываются имя, почта и время из примера в контракте,
  а не то, что ввёл гость — на экране об этом сказано явно;
- настоящий конфликт `409 slot_taken` возникнуть не может. Чтобы ветки ошибок
  из контракта не остались непроверенными, в dev-сборке в шапке есть селектор
  сценария ответа: успешная запись, `slot_taken`, `slot_not_in_grid`,
  `slot_out_of_window`, `not_found`.

В обычном режиме (`npm run dev`) ничего этого нет: бэкенд хранит состояние,
бронь исчезает из календаря и появляется в списке встреч, а `slot_taken`
возникает по-настоящему. Селектор сценариев и предупреждение о примерных
данных на экране не показываются.
