# Как вносить изменения

## Формат коммитов — Conventional Commits

Сообщения коммитов разбираются автоматически: по ним release-please считает
следующую версию и собирает changelog. Формат обязателен и для людей,
и для коммитов, которые делает агент.

```
<тип>(<скоуп>)<!>: <заголовок>

<тело>

<футеры>
```

### Типы

| Тип | Когда | Влияние на версию |
|-----|-------|-------------------|
| `feat` | новая возможность для пользователя | minor |
| `fix` | исправление ошибки | patch |
| `perf` | ускорение без смены поведения | patch |
| `docs` | только документация | — |
| `refactor` | переработка без смены поведения | — |
| `style` | форматирование, пробелы, порядок импортов | — |
| `test` | тесты и их инфраструктура | — |
| `build` | сборка, Dockerfile, зависимости | — |
| `ci` | workflow и CI-обвязка | — |
| `chore` | всё остальное служебное | — |
| `revert` | откат предыдущего коммита | — |

Ломающее изменение — `!` после скоупа и/или футер `BREAKING CHANGE:` с описанием.
Пока версия младше `1.0.0`, такое изменение поднимает minor, после — major.

### Скоупы

Необязательны, но если указаны — только из списка:
`contract`, `backend`, `frontend`, `e2e`, `ci`, `docs`, `deps`.

Скоуп `main` зарезервирован за release-please: он так называет свой релизный PR.

### Заголовок

- на русском, в повелительном наклонении: «добавить», а не «добавил» / «добавление»;
- со строчной буквы, без точки в конце;
- до 100 символов вместе с типом и скоупом;
- описывает результат для пользователя или разработчика, а не список файлов.

### Тело и футеры

Тело — по желанию, через пустую строку, строки до 100 символов. Нужно там,
где неочевидно **почему** сделано именно так. Футеры — `BREAKING CHANGE:`,
ссылки на задачи, трейлеры авторства.

### Примеры

```
feat(frontend): показывать часовой пояс владельца рядом со слотами

fix(backend): не отдавать слоты, пересекающиеся с бронью другого типа события

Проверка занятости смотрела только на брони того же типа, поэтому
календарь показывал время, на которое запись всё равно падала с 409.

docs: описать пользовательские сценарии для e2e

feat(contract)!: убрать из BookingCreate необязательное поле source

BREAKING CHANGE: клиенты, отправлявшие `source`, получат 400 validation_failed.
```

Плохо: `правки`, `Added tests`, `WIP`, `fix: исправил баг.`

## Как формат проверяется

В трёх местах, все три обязаны быть зелёными:

1. **Локально** — хук `.husky/commit-msg` гоняет commitlint при каждом коммите.
   Ставится сам при `npm install` в корне (скрипт `prepare`).
2. **В CI** — джоба `commitlint` проверяет все коммиты ветки PR.
3. **Заголовок PR** — джоба `pr-title`. В `main` мёрджим squash-мёрджем, поэтому
   в историю уезжает именно заголовок PR, и читать его будет release-please.

Правила лежат в [`commitlint.config.js`](commitlint.config.js).
Мёрдж-коммиты commitlint пропускает сам.

Проверить сообщение, не делая коммит:

```bash
echo "feat(e2e): добавить сценарий отмены брони" | npx commitlint
```

Если хук мешает в исключительной ситуации, его можно обойти
(`git commit --no-verify`), но CI всё равно не пропустит.

## Коммиты агента

Агент (Claude Code) подчиняется тем же правилам — они продублированы
в [`CLAUDE.md`](CLAUDE.md), который агент читает автоматически. Дополнительно:

- агент коммитит только по явной просьбе, не по своей инициативе;
- в футер добавляется трейлер соавторства:

  ```
  Co-Authored-By: Claude <noreply@anthropic.com>
  ```

- один коммит — одно осмысленное изменение; «заодно поправил ещё вот это»
  выносится в отдельный коммит со своим типом.

## Ветки и PR

- Работаем в ветках от `main`, имя — `<тип>/<короткое-описание>`
  (`feat/otmena-broni`, `fix/slot-timezone`).
- Заголовок PR — по Conventional Commits, он же станет коммитом в `main`.
- В `main` мёрджим **squash-мёрджем**.
- Перед PR прогнать сквозные сценарии: `npm run e2e`.

## Релизы

Версию и changelog ведёт release-please, руками их править не нужно.
После мёрджа в `main` бот создаёт (или обновляет) PR `chore(main): release X.Y.Z`
с обновлённым `CHANGELOG.md` и версией во всех местах, где она записана.
Мёрдж этого PR ставит тег `vX.Y.Z` и публикует GitHub Release.

Версия одна на весь репозиторий и дублируется в `package.json`,
`frontend/package.json` и `backend/app/main.py`; источник правды —
`.release-please-manifest.json`.
